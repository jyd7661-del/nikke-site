### 수정·삭제가 "안 되던" 진짜 이유

유저 제보: "게시판이랑 조합 올리는 곳이 수정·삭제가 안 된다."
**권한 문제가 아니었습니다.** DB 정책(`posts_update_own` / `posts_delete_own` /
`combos_update_own` / `combos_delete_own`)은 처음부터 `auth.uid() = user_id` 조건으로
정상 설정돼 있었고, **`lib/board.js`·`lib/combos.js`에 함수가, 화면에 버튼이 없었을 뿐**입니다.
같은 착각을 반복하지 않으려면 **정책을 먼저 의심하지 말고 코드에 함수가 있는지부터 보세요.**

추가한 것: `updatePost` / `deletePost` / `updateComment` / `deleteComment` /
`updateCombo` / `deleteCombo`. 화면에는 글 상세·댓글·조합 카드에 본인 것만 수정/삭제 버튼.

⚠️ **자식 레코드를 앱에서 먼저 지우지 마세요.** `comments_post_id_fkey`와
`combo_votes_combo_id_fkey`는 **이미 `ON DELETE CASCADE`** 입니다(2026-08-09 확인).
앱에서 먼저 지우려 하면 `comments_delete_own` / `votes_delete_own` 정책 때문에 **내 것만**
지워지고 남의 것은 남아, 조합은 외래키 위반으로 삭제가 실패하고 글은 "지웠는데 댓글이 남는"
상태가 됩니다. 캐스케이드는 RLS를 거치지 않아 남의 것까지 정상 정리됩니다.
실측: 글 소유자가 삭제 → 남이 쓴 댓글까지 함께 삭제됨.

### 서킷 브레이커의 남은 위험 (2026-08-09 확인)

RLS를 고친 뒤 Supabase 어드바이저에 **새 WARN이 하나 생겼습니다** —
`increment_ai_daily_budget()`을 anon이 실행할 수 있다는 것. **이건 의도한 설계입니다**
(라우트가 anon 키로 호출해야 함). 다만 잔여 위험이 있습니다:

**누군가 `/rest/v1/rpc/increment_ai_daily_budget`을 직접 반복 호출해 카운터를 부풀리면
그날의 AI 설명 생성이 조기에 멈춥니다.** IP당 30회 제한은 이 경로를 거치지 않습니다.

**그래도 이 방향이 낫다고 판단한 이유**: 반대로 update를 열어두면 카운터를 0으로 만들어
**상한 자체를 무력화**할 수 있고 그건 곧 비용입니다. 지금 구조에서 가능한 악용은
"부풀리기"뿐이고, 그 결과는 **비용이 아니라 가용성**(설명이 담백해짐)입니다. 게다가 상한에
걸려도 조합·점수·근거는 그대로 나갑니다. 나쁜 쪽으로 실패하게 두는 편을 택했습니다.

**제대로 막으려면**: Vercel에 `SUPABASE_SERVICE_ROLE_KEY`를 넣고 이 RPC만 service role로
호출한 뒤, anon의 EXECUTE 권한을 회수하면 됩니다. 비밀키를 하나 더 두는 결정이라 보류했습니다.

### 별건 — `combo_scores` 뷰가 SECURITY DEFINER (미해결)

같은 어드바이저에서 **ERROR** 등급으로 잡힙니다. 뷰가 조회자가 아니라 **생성자의 권한과 RLS로**
동작해서, 뷰를 통하면 원래 못 볼 데이터가 보일 수 있습니다. 조합 투표 집계 뷰라 민감도는
낮아 보이지만 확인이 필요합니다. 이번 작업 범위 밖이라 손대지 않았습니다.

### 남은 개선 사항

- **`limited` 태그 미사용** — 미보유 캐릭터 안내에 활용 가능
- **낭비 판정 부분 점수** — 0/전부가 너무 거칠지만 근거 있는 수치가 없어 보류
- **콘텐츠 보강** — 애드센스 검토에 유리. 지금은 도구 성격이 강해 "콘텐츠가 얇다" 판정 위험
- **빈칸 조합의 구조적 유리함** — 로스터에서 최적으로 채워지므로 5인 확정 조합보다 유리.
  전 캐릭터 보유 가정 시 상위 1~3위가 전부 빈칸 4개짜리. 나중에 "확정 조합만 보기" 필터가 필요할 수 있음
