### 캐싱 (`ai_explain_cache` 테이블)

엔진이 결정적이라 같은 입력 → 같은 출력입니다. **캐시 키는 로스터가 아니라 "AI에게 실제로
보낸 입력"의 SHA-256**(모드/언어/멤버/근거/노트). 그래서:
- 서로 다른 로스터라도 결론이 같으면 캐시 공유
- 엔진·데이터가 바뀌어 근거가 달라지면 키가 자동으로 바뀜 → **수동 무효화 불필요**
- 프롬프트를 크게 바꿀 때만 `buildCacheKey`의 `v` 값을 올림 (현재 v2)

실측: 미스 8.5초 → **히트 1.9초**, 비용 0.

주의 두 가지:
- **캐시 적중은 하루 사용 횟수를 깎지 않습니다** (비용이 0이므로)
- **AI 호출 실패 시 폴백 문장은 캐시에 저장하지 않습니다** (저장하면 그 조합에 열화된 설명이 영구히 박힘)

### 일일 총 호출 상한 (서킷 브레이커) — 2026-08-09 도입 완료

IP당 30회 제한만으로는 IP가 많아지면 총액을 못 막습니다. 전역 상한을 넣었습니다.

- `DAILY_GLOBAL_LIMIT` = `AI_DAILY_GLOBAL_LIMIT` 환경변수, **기본 1,000회/일**
  (1건 약 4.9원 → 하루 약 4,900원 / 월 약 14.7만원. "감수할 금액"이 아니라 **폭주를 끊는 천장**)
- **캐시 적중은 세지 않고 막지도 않습니다.** 상한 확인은 캐시 조회 뒤, AI 호출 직전에만 합니다
- **상한에 걸려도 에러를 내지 않습니다.** `fallbackReasoning`(근거 문장)으로 대체하고
  응답에 `budgetExhausted: true`를 실어 화면에 안내를 띄웁니다. 조합 구성·점수·근거는 전부
  엔진이 정하므로(§2-1) AI 문장이 빠져도 결과물의 핵심은 그대로입니다
- 이 폴백 문장은 **캐시에 저장하지 않습니다**(기존 규칙과 동일)

**테이블: `ai_daily_budget`** (`supabase/ai_daily_budget_migration.sql`, **2026-08-09 실행 완료**)

```sql
ai_daily_budget(usage_date date primary key, count integer)
increment_ai_daily_budget()  -- security definer, 원자적 upsert 증가
```

**왜 RPC로 증가시키나:** select 후 update 방식은 동시 요청에서 갱신이 유실돼 카운터가 실제보다
적게 남습니다. 서킷 브레이커에서 그건 "보호가 조용히 약해지는" 방향이라 특히 나쁩니다.

**왜 select 정책만 열었나:** anon 키는 프론트 번들에 그대로 들어갑니다. insert/update를 열면
누구나 카운터를 0으로 만들어 상한을 우회하거나, 반대로 큰 값을 넣어 서비스를 막을 수 있습니다.
증가는 `security definer` 함수로만 가능합니다.
**실제로 anon 역할로 확인했습니다** — RPC 호출은 되고, 직접 update/insert는 RLS가 막습니다.

⚠️ **조회 실패 시에는 열어둡니다**(Supabase가 흔들렸다고 사이트가 멈추는 건 과함).
대신 `[AI_BUDGET]` 태그로 로그를 남깁니다. **배포 후 이 태그가 반복해서 찍히면 보호가 안 걸리고
있다는 뜻이니 즉시 확인하세요.**
